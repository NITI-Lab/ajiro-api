# Ajiro API（仮称）要件定義書

Nov 16, 2026 · @Yuya

## 1. 概要・背景・目的

Ajiro API（仮称）は、Claude Code / Codex がバックエンドのコードからAPI定義・回帰テスト・モックを自動生成し、受託チーム内とクライアントへ仕様を共有するためのローカルファーストなツールです。まず無料のOSS CLIとClaude Codeスキルを公開して反応を見て、有料のデスクトップGUIはAjiro（WBS・タスク管理）のリリース後に出します。

**背景（解決する痛み）**

- AIにAPIを実装させると、全エンドポイントの疎通確認と、壊れていないかの確認が人手のまま残る。
- 受託では、バックエンド担当がフロント担当（外注を含む）やクライアントにAPI仕様とサンプルレスポンスを渡す作業が必ず発生する。
- 既存のHTTPクライアントは「人間がGUIでリクエストを送る」前提で作られていて、AIエージェントが読み書きする前提になっていない。

**ポジショニング**

「軽くてGit管理できるHTTPクライアント」では無料OSSに埋もれます。そこで「AIコーディングエージェントのための、API検証と仕様共有の基盤」と位置付けます。人間がGUIを触るのは、確認・共有・修正のときだけにします。

**Ajiroシリーズでの位置付け**

- Ajiro（WBS・タスク管理）の姉妹製品とする。
- Phase 3で、タスクID（例: TSK-012）とテスト結果・モックを結び付ける。

**目的（この文書の範囲）**

- Phase 1（OSS CLIとスキル）の要件を、実装に着手できる粒度で確定する。
- Phase 2以降は、作るかどうかの判断基準と機能の大枠だけを定める。

## 2. 対象ユーザーと利用シーン

主な対象は、5〜20名規模の受託開発チームで、Claude CodeやCodexで日常的に実装している人たちです。Phase 1の利用者はバックエンド担当だけで、フロント担当とクライアントはPhase 2で対象に入ります。

| ペルソナ | 役割 | 今の困りごと | 使う場面 | 対象Phase |
| --- | --- | --- | --- | --- |
| A. バックエンド担当 | AIでAPIを実装する | AIが書いたAPIの動作確認と、修正後の度重なる回帰確認が手作業 | 実装直後にエージェントへテスト生成と実行を任せる。CIでも回す | 1 |
| B. フロント担当（外注含む） | 画面を実装する | APIの完成待ち。仕様が口頭やチャットで飛んでくる | ローカルモックにつないで先行開発する | 2 |
| C. PM・代表 | 進捗と品質に責任を持つ | どのAPIが動いているか見えない。ツール代が人数分増える | テスト結果をタスクと並べて見る | 3 |
| D. クライアント・協力会社 | 仕様を受け取る | Swaggerの環境を用意できない。Excelの仕様書は古くなる | 送られてきたHTML仕様書をブラウザで開くだけ | 2 |

**代表的な利用の流れ（Phase 1）**

1. バックエンド担当がClaude Codeに新しいエンドポイントを実装させる。
2. スキルに従って、エージェントが `ajiro-api scan` でルーティングを読み取り、YAML定義を生成・更新する。
3. `ajiro-api test` で全エンドポイントを叩き、失敗があればエージェントが自分で直して再実行する。
4. 生成されたYAMLをコードと一緒にGitへコミットし、CIでも同じテストを回す。

## 3. 競合と差別化

差別化の軸は三つです。AIエージェントが主な利用者であること、独自形式ではない標準YAMLであること、チーム定額で人数課金をしないことです。料金は2026年11月時点の公式ページで確認しました（年払い表示）。

| 製品 | 無料でできること | チーム利用の料金 | 保存形式 | 狙える弱点 |
| --- | --- | --- | --- | --- |
| [Postman](https://www.postman.com/pricing/) | 1ユーザーのみ。チーム作成不可（2026年3月に変更、[公式ドキュメント](https://learning.postman.com/docs/billing/about-plans)） | Team $19/人・月 | クラウド中心、Collection JSON | 少人数チームでも共有で有料化。乗り換え需要がある |
| [Bruno](https://usebruno.com/pricing) | OSS版。公開Gitプロバイダーとの連携 | Pro $6・Ultimate $11/人・月 | 独自形式 `.bru` | 独自形式でAIが書きにくい。非公開Git連携は有料 |
| [Yaak](https://yaak.app/blog/simplifying-pricing) | 個人利用 | 業務利用は有料ライセンス（現行価格は要確認） | ローカルファイル | 人間向けGUIが中心で、エージェント前提ではない |
| Hoppscotch | Web版とセルフホスト | 要確認 | ブラウザおよびサーバー | ローカルのGit運用とは別の方向性 |
| **Ajiro API** | CLI・スキル・テスト実行をすべて無料（MIT） | GUIをチーム定額（「9. 料金」参照） | 標準YAML（OpenAPIと相互変換） | — |

**狙わないこと**

- 手動でリクエストを組み立てる使い勝手ではPostmanやYaakと競わない。
- GraphQL、gRPC、WebSocketはPhase 1の対象外とする。

## 4. 製品構成とフェーズ

製品は、無料のOSS（CLI・スキル・MCP）と、有料のデスクトップGUIの2層です。Phase 1の工数は3週間を上限とし、Ajiroの2027年3月1日リリースを遅らせないことを最優先にします。

## 5. 機能要件（Phase 1：OSS CLIとスキル）

Phase 1の完了条件は、「Claude CodeがサンプルリポジトリのAPIを実装してから、YAML生成・全件テスト・失敗の自己修正までを人手なしで完走すること」です。優先度はMust（初回公開に必須）、Should（公開後1ヶ月以内）、Could（反応次第）の3段階です。

| ID | 機能 | 内容 | 優先度 |
| --- | --- | --- | --- |
| F1-01 | `init` | 設定ファイル `ajiro-api.yaml` と `api/` ディレクトリを作る。フレームワークを自動判定する | Must |
| F1-02 | `scan` | ルーティングを静的解析し、エンドポイント一覧（メソッド・パス・パラメータ）をYAMLに書き出す。手書き部分は上書きしない | Must |
| F1-03 | 対応フレームワーク | Next.js Route Handlers、Hono、FastAPI。次にExpressとGo（net/http・chi・Echo） | Must（3種）／Should（残り） |
| F1-04 | `test` | YAMLのリクエストを順に実行し、ステータス・ヘッダ・ボディを検証する。終了コードで成否を返す | Must |
| F1-05 | 検証方法 | 完全一致、JSON Schema、JSONPathでの部分一致、スナップショット比較（IDや日時など変わる項目は除外指定） | Must |
| F1-06 | 変数と環境 | `local`・`staging` などの環境切り替え。秘密情報は `.env` 参照でYAMLに書かない | Must |
| F1-07 | リクエストの連鎖 | ログインで得たトークンを後続に渡すなど、前のレスポンスの値を使う | Must |
| F1-08 | 機械向け出力 | `--json` で失敗箇所、期待値、実際の値、該当するソースの位置を返す。エージェントがそのまま修正に使える形にする | Must |
| F1-09 | Claude Codeスキル | `SKILL.md`。実装後に scan、test、修正、再実行の順で回す手順と、YAMLの書き方を含む | Must |
| F1-10 | Codex対応 | `AGENTS.md` に貼れる同等の手順書 | Must |
| F1-11 | MCPサーバー | scan・test・listをMCPツールとして公開する | Should |
| F1-12 | CI向け出力 | JUnit XMLとGitHub Actionsのサンプルワークフロー | Should |
| F1-13 | OpenAPI変換 | OpenAPI 3.xとの双方向変換（import と export） | Should |
| F1-14 | 簡易モック | `mock` でYAMLのサンプルレスポンスを返すだけのサーバーを立てる（本格版はPhase 2） | Could |

**コマンドの例**

```bash
ajiro-api init
ajiro-api scan --framework hono src/
ajiro-api test --env local --json
```

Phase 2以降は、Phase 1の反応（「10. KPI」の判断基準）を満たしたときだけ着手します。ここでは大枠のみ定め、詳細は着手時に書き直します。

| ID | 機能 | 内容 | 提供先 | Phase |
| --- | --- | --- | --- | --- |
| F2-01 | ローカルモックサーバー | ワンクリック起動。遅延やエラーの再現、シナリオ切り替えができる | 有料 | 2 |

## 7. YAMLスキーマ案

エンドポイント1つにつきYAMLファイル1つとし、`api/<リソース>/<メソッド>-<パス>.yaml` に置きます。ファイルを小さく分けるのは、Gitの競合を減らし、AIが編集する範囲を狭くするためです。`source` はscanが書き、`tests` は人とAIが書く欄として分けます。

```yaml
# api/users/post-users.yaml
version: 1
id: users.create
request:
  method: POST
  path: /users
  headers:
    Authorization: Bearer {{ auth.token }}
  body:
    name: Taro
    email: taro@example.com
source:            # scan が自動で更新する欄
  framework: hono
  file: src/routes/users.ts
  line: 42
tests:             # 人とAIが書く欄（scan は触らない）
  - name: 正常に作成できる
    expect:
      status: 201
      body:
        schema: ./schemas/user.json
        match:
          $.email: taro@example.com
      ignore: [$.id, $.createdAt]
    capture:
      userId: $.id
  - name: メール重複は409
    request:
      body: { email: dup@example.com }
    expect:
      status: 409
mock:              # Phase 2 のモックサーバーで使う
  default: { status: 201, body: { id: usr_001, name: Taro } }
  scenarios:
    conflict: { status: 409 }
```

- スキーマ自体をJSON Schemaで公開し、エディタの補完とAIの構文ミス検出に使う。
- `version` でスキーマの互換性を管理する。破壊的な変更には移行コマンドを用意する。

## 8. 非機能要件・技術構成

CLIはRustで書き、Phase 2のTauriアプリとAjiro本体でコア部分を共有します。サーバーにAPI定義やテスト結果は一切置きません。

| 項目 | 方針 |
| --- | --- |
| 実装言語 | Rust（単一バイナリ。実行時のNodeやPythonを要求しない） |
| ルーティング解析 | tree-sitterによる静的解析（TypeScript・Python・Go）。フレームワークごとに解析ルールを分ける |
| 配布 | GitHub Releases（macOS・Windows・Linux）、npm（`npx ajiro-api`）、Homebrew、cargo |
| 性能目標 | 100エンドポイントのscanを3秒以内。起動は0.1秒以内 |
| セキュリティ | 秘密情報は `.env` 参照のみ。出力ログではトークンやパスワードを伏せ字にする |
| 利用統計 | 初期状態はオフ。同意した場合のみ、匿名のコマンド実行回数を送る |
| Phase 2 GUI | Tauri v2 + Rust + React（Ajiroと同じ構成）。コード署名はmacOSとWindowsで行う |
| ライセンス認証 | Ajiroと同じCloudflare Workersの最小構成サーバーを共用する |
| テスト | 対応フレームワークごとにサンプルリポジトリを用意し、scan結果のスナップショットで回帰を防ぐ |

## 9. 料金・ライセンス方針

CLIとスキルはMITライセンスで完全無料とし、有料にするのはPhase 2のGUIだけです。人数ごとの課金はしず、Ajiroと同じくチーム単位の定額にします。以下の金額はたたき台で、Phase 2の着手前に確定します。

| プラン | 内容 | 価格案（税別） |
| --- | --- | --- |
| OSS | CLI、スキル、MCP、インポーター、クレジット付きHTML仕様書 | 無料 |
| Team | GUI、モックサーバー、テスト結果ビュー、クレジットの非表示。5名まで | 月額1,480円 |
| Ajiroセット | Teamに加えてAjiro本体とタスク連携。5名まで | 月額2,480円 |

- 決済はAjiroと同じくStripe直接、ライセンスは手動発行から始める。
- 比較の目安：Postman Teamは5名で月$95、Bruno Proは5名で月$30（いずれも年払い、「3. 競合」参照）。
- 6名以上の料金体系は、Ajiroの「複数プロジェクトをまとめて管理する」料金設計に合わせて決める。

## 10. 集客方針とKPI・判断基準

公開から8週間で下の「Phase 2着手の目安」を半分以上満たしたら、有料GUIに着手します。広告費はかけず、代表個人のSNS発信も前提にしません。

**集客経路（フォロワー不要のもののみ）**

- Zenn（NITIのPublication名義）、Qiita、NITI Journal
- awesome-claude-code などのawesome系リスト、Claude Codeプラグイン・MCPのディレクトリ、GitHub Topics
- Hacker News（Show HN）、Reddit（r/ClaudeAI、r/webdev）に各1回
- connpassのAI駆動開発系勉強会でのLT

| 指標 | 測り方 | Phase 2着手の目安（8週間） |
| --- | --- | --- |
| GitHubスター数 | GitHub | 300 |
| 週間ダウンロード数 | npmとGitHub Releasesの合計 | 200/週 |
| 外部からのIssue・PR | GitHub | 20件 |
| GUI・モック・仕様書を求める声 | Issueと記事コメントの件数 | 10件 |
| Zenn記事の反応 | いいね数 | 100 |

- 有料化後は「インストール数→無料版GUIの利用→Team課金」の転換率を見る。開発者向けツールの転換率は1〜2%を前提に計画する。
- 目安の数値は仮置き。公開後2週間の実績を見て見直す。
